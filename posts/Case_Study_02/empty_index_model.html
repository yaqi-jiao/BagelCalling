Case Study | How to take parameters from input

description: embrace argparse

Case

When I took Python lessons last year, our teacher taught us to use sys.argv to set input parameters instead of using hard-coded values. It worked, but in practice, it quickly became inconvenient.

For example, here’s one of my practice scripts:

        texts = sys.argv[2]

    with open(indice_file, "r") as f_indices, open(texts, "r") as f_texts:

With sys.argv, all parameters depend on your memory. In other words, if you let another person run this script without showing a usage example, it’s hard to use correctly.

During my project, when I read my senior’s code, I found it very well written. I take some sections as learning material. She used argparse in two parts of the code. We can look at them and understand why.

Study

some basic knowledge

# minimal workfolw

import argparse  # package preparation

parser = argparse.ArgumentParser()   # create a parser
parser.add_argument("--parameters_you_want_to_specify")  # defines an arguement

args = parser.parse_args()           # parse command-line input

return args

After setting this up, you can run the script in the console with parameters.

  • if you want your parameter to be a must: parser.add_argument("--parameters_you_want_to_specify", required=True)

  • if you want to set default value:

    parser.add_argument("--parameters_you_want_to_specify", default="default_value_you_want_to_set")

  • if you want to control parameter type (take float as an example): parser.add_argument("--parameters_you_want_to_specify", type=float)

after setting parameters, how to extract them from input?

After defining arguments using add_argument(), argparse reads the input and maps each argument to a Python attribute.

For example: --input_dir data/test in CLI becomes args.input_dir == "data/test”

Extraction is done using args = parser.parse_args() , and access via args.parameter_name

how to process complex path parameter from input

When dealing with file paths, treating them as plain strings can be error-prone.

In this case, be careful: she does not define --input_dir in params.py. Instead, she defines another parser in run_summary_one_conn.py and does not reuse params.py.

This is likely for function separation and path handling. We will discuss this in another case study.

important: how to support both configuration file and command line parameters

Example:

parser.add_argument('--model_name', type=str, default=essential_params.get("model_name", "TEST_SIR_baseline_hypertune30000"), help='...')

In this command, the configuration file (in this case, User_input_setting.txt) first replaces the hardcoded fallback and becomes the default value used by argparse. At this stage, the configuration file has already replaced the hardcoded fallback.

Then when we call args = parser.parse_args() in main(), argparse reads the command-line input. If the user provides --model_name in the CLI, this CLI value overwrites the default value that was prepared earlier.

So the actual priority is:

command-line arguments > config file > hardcoded default

In this design, the configuration file is used to build argparse defaults, while command-line input still has the final control.

function or not

You may notice that sometimes argparse is used directly in main() (like in run_summary_one_conn.py), while in larger programs it is wrapped into a function.

This depends on:

  • code complexity
  • number of parameters
  • need for reuse

In params.py, parse_arguments() is defined, which allows additional processing:

args, unknown = parser.parse_known_args()
args = make_output_dir(args,proj_path, script_dir, hypertune)

First, parse_known_args() creates args, then extra attributes are added (e.g., proj_path, script_dir, hypertune).

my usage

def parse_args():
    """
    Parse command-line arguments.

    """
    parser = argparse.ArgumentParser(
        description="Reduce SIR input pkl by dropping regions using names."
    )
    parser.add_argument("--input-pkl", required=True, type=str)
    parser.add_argument("--drop-names", nargs="+", default=None)
    parser.add_argument("--drop-names-txt", type=str, default=None)
    parser.add_argument("--process-each-line", action="store_true")
    parser.add_argument("--show-all-names", action="store_true")
    parser.add_argument("--allow-missing-drop-names", action="store_true")
    
    return parser.parse_args()

Note: I return parser.parse_args() directly instead of assigning it to args.

takeaways

  1. When you have many scripts, consider separating parameter processing into an individual module. But don’t be too rigid—split only when needed.
  2. Separate optional parameters clearly and document them clearly, never trust your memory.
